01 / Problem

为什么这个项目
能打到面试官

应届简历里 90% 是「XXX 商城 / XXX 后台」。一个被真实项目 npm i 下来的工具包， 能一次性证明你懂构建原理、有 CI 意识、能产出量化收益 —— 这三件事恰恰是 CRUD 项目证明不了的。

P1

体积是悄悄变大的

没人 review 依赖。import _ from 'lodash' 一行代码带进来 71 KB， 三个月后首屏 JS 从 600 KB 涨到 1.4 MB，直到线上 LCP 报警才被发现。

P2

现有工具只会「看」

webpack-bundle-analyzer / rollup-plugin-visualizer 都只出图， 闸口在人的自觉上。size-limit 能卡总量，但说不清是哪个包、经由哪条 import 链变大。

P3

归因数据本身在骗人

按压缩前模块大小累加，terser 压缩后比例会大幅失真 —— lodash 压完可能只剩 40%， 而业务代码几乎不缩。报告会指向错误的优化目标。

02 / Scope

能力地图 · 三级范围

MVP 只做 L1 + L2，L3 有余力再补。如果时间只剩三周，保 W3（字节归因）+ W4（门禁）+ W6（报告）， 其余都可以砍 —— 这三块构成了完整的技术叙事闭环。

MODULE 01 · 必做 Volume Gate

体积守护 Budget Gate

把「性能预算」从口号变成 CI 里真实会红的那一行。

  • 四类预算匹配：单产物 / 入口 / 正则分组 / 全局总量
  • 真实压缩体积：worker 池并行 gzip level 9 + brotli，不用 size×0.3 估算
  • 增量基线：.guardian/baseline.json 入库，increaseLimit: '5%'
  • 分级拦截：error → exit 1；warn → 黄字不阻断；本地提示 / CI 真拦
MODULE 02 · 核心竞争 Dependency Intel

依赖分析与归因

不只告诉你「变大了」，而是「谁、从哪来、怎么改」。

  • 字节级体积归因：sourcemap 逆向映射，误差 22% → 3%
  • 引入链追溯：why echarts 打印最短依赖路径
  • 重复版本：同名多版本检测 + 给 pnpm overrides 命令
  • 循环依赖：module graph 上跑 Tarjan SCC，输出环路径
  • 未使用依赖：声明 vs 真实 import 差集（带 sideEffects 白名单）
MODULE 03 · 差异化 Rule Engine

规则引擎（可插拔）

每条内建规则都输出「病因 + 药方」，而不是干巴巴一条警告。

  • duplicate-dep / circular-dep / unused-dep
  • cjs-bundled → 提示 tree-shaking 失效
  • 用户可用 .guardianrc.ts 覆盖级别 / 注入自定义规则

05 / Core Algorithm

★ 基于 SourceMap 的
字节级体积归因

这是整个项目唯一有技术壁垒的地方，也是面试时最能拉开差距的一段。 把下面这段截图放进 README，比写十行「熟悉 Vite」都有用。

packages/core/src/attribution.ts TS 
// 输入：OutputChunk.code + OutputChunk.map
// 输出：Map<sourcePath, utf8Bytes>  —— 产物里每个字节的主人

const B64 = 'ABCDEFGHIJ…xyz0123456789+/';
const SHIFT = 5, MASK = 31, CONT = 32;

function decodeVLQ(mappings: string) {
  const lines: Array<Array<[number,number,number,number]>> = [[]];
  let srcIdx = 0, srcLine = 0, srcCol = 0;
  for (let i = 0, line = 0, genCol = 0; i < mappings.length;) {
    const ch = mappings[i];
    if (ch === ';') { genCol = 0; lines[++line] = []; i++; continue; }
    if (ch === ',') { i++; continue; }
    const out: number[] = [];
    for (let n = 0; n < 4; n++) {      // genColΔ srcIdxΔ srcLineΔ srcColΔ
      let r = 0, shift = 0, c: number;
      do {
        c = B64.indexOf(mappings[i++]);
        r += (c & MASK) << shift;
        shift += SHIFT;
      } while (c & CONT);                // 最高位是连续位
      out.push(r & 1 ? -(r >>> 1) : r >>> 1);   // 末位是符号位
    }
    genCol += out[0]; srcIdx += out[1];
    srcLine += out[2]; srcCol += out[3];
    lines[line].push([genCol, srcIdx, srcLine, srcCol]);
  }
  return lines;
}

export function attribute(chunk: OutputChunk) {
  const map = chunk.map!;
  const lines = decodeVLQ(map.mappings);
  const raw = chunk.code.split('\n');
  const acc = new Map<string, number>();

  lines.forEach((segs, ln) => {
    const text = raw[ln] ?? '';
    for (let i = 0; i < segs.length; i++) {
      const start = segs[i][0];
      const end = i + 1 < segs.length
        ? segs[i + 1][0] : text.length;
      const src = map.sources[segs[i][1]] ?? '<runtime>';
      // 关键：按 UTF-8 字节算，不能用 String.length（中文会翻倍）
      const bytes = Buffer.byteLength(text.slice(start, end));
      acc.set(src, (acc.get(src) ?? 0) + bytes);
    }
    const first = segs[0]?.[0] ?? 0;
    if (first > 0) // 行首未映射前缀 → banner / runtime
      acc.set('<runtime>', (acc.get('<runtime>') ?? 0)
        + Buffer.byteLength(text.slice(0, first)));
  });
  return acc;   // → 再交给 pkg-resolve 聚合成 npm 包粒度
}
1map.mappings 是 VLQ 编码串：; 分隔 generated 行，, 分隔 segment。
2每个 segment 存的是 增量值（Δ），必须累加才能得到绝对行列。
3相邻两个 segment 之间的列区间 [col_i, col_{i+1}) 归属同一个源模块。
4用 Buffer.byteLength 而非 .length —— 中文注释按 UTF-8 是 3 字节。
5未被任何 segment 覆盖的尾部 + license 注释 → 归入 <runtime> 桶。
6pkg-resolve 归一化：.pnpm/echarts@5.5.0/node_modules/echarts/… → {pkg, version}。
为什么不用 module.code.lengthTrade-off
// 朴素做法：按模块「压缩前」大小累加
// 问题：terser 会 mangle / drop console / inline
//       lodash 压完只剩 40%，业务代码几乎不缩
